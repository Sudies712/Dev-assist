## 1. 引言

### 1.1 编写目的

本文档为平台的概要设计说明书（High-Level Design），在需求规格说明书 V2.1 基础上确定系统"怎么做"：总体架构、模块划分与协作、关键技术集成方案、数据库与接口组织、安全与部署设计，作为后续详细设计、编码实现与测试的依据。

### 1.2 设计范围

**覆盖**：系统总体架构、后端分层与包结构、模块划分与依赖、AI 模块架构与 RAG 管道、前端架构、接口规范（概要）、数据库设计（概要）、安全设计、部署设计、非功能性设计实现。

**不含（留待详细设计文档）**：类图、时序图、方法级伪代码、完整建表 SQL、接口请求/响应字段级定义、UI 视觉稿。

### 1.3 术语

补充设计术语（需求文档未单列术语节）：

| 术语 | 含义 |
|------|------|
| 三层架构 | 表现层（Controller）/ 业务层（Service）/ 数据访问层（Mapper） |
| DTO / VO / PO | 数据传输对象 / 视图对象 / 持久化对象（与数据库表对应） |
| IoC / DI | 控制反转 / 依赖注入 |
| AOP | 面向切面编程，用于横切关注点（日志、权限、事务） |
| SSE | Server-Sent Events，AI 流式输出通道 |
| 策略模式 | AI 助手抽象所用模式，统一接口多实现 |

### 1.4 参考文献

- 需求规格说明书 V2.1（本项目，`01-需求分析文档.md`）
- Scrum Guide、LangChain4j 官方文档、Sa-Token 文档、MyBatis-Plus 文档、Qdrant 文档、vue-pure-admin 文档

### 1.5 设计原则

1. **分层清晰**：Controller / Service / Mapper 职责单一，禁止跨层调用
2. **高内聚低耦合**：业务模块独立子包，模块间通过 Service 接口协作
3. **业务与 AI 解耦**：AI 模块通过调用业务 Service 获取数据，不直接操作业务表
4. **配置与 Prompt 外置**：环境配置、AI Prompt 模板与代码分离
5. **依赖倒置**：面向接口编程，便于替换实现（如 Embedding/Chat 模型可切换）

## 2. 系统总体设计

### 2.1 系统架构

采用前后端分离的三层架构，单体部署。第三方大模型能力通过 LangChain4j 接入，不改变主体业务流程。

```text
┌──────────────────────────────────────────────────────────┐
│                    浏览器（最终用户）                       │
└─────────────────────────┬────────────────────────────────┘
                          │ HTTPS
┌─────────────────────────┴────────────────────────────────┐
│         前端  vue-pure-admin v7（Vite 构建 SPA）            │
│   Views 视图 │ Pinia 状态 │ Router 路由 │ HTTP + SSE 客户端 │
└─────────────────────────┬────────────────────────────────┘
                          │ RESTful API + SSE（/api/*，Sa-Token 鉴权）
┌─────────────────────────┴────────────────────────────────┐
│              后端  Spring Boot 4.1（单体）                  │
│                                                            │
│   ┌──────────────────────────────────────────────────┐    │
│   │  Controller 表现层（接收 / 参数校验 / 响应封装）    │    │
│   ├──────────────────────────────────────────────────┤    │
│   │  Service 业务层（业务逻辑 / 事务 / 权限）          │    │
│   ├──────────────────────────────────────────────────┤    │
│   │  Mapper 数据访问层（MyBatis-Plus）                 │    │
│   └──────────────────────────────────────────────────┘    │
│                                                            │
│   横切：AOP（操作日志 / 数据范围）│ 全局异常 │ Sa-Token 鉴权  │
│   AI 模块：LangChain4j（ChatModel / Embedding / RAG / Tool）│
└──┬──────────────┬──────────────┬──────────────┬──────────┘
   │              │              │              │
   ▼              ▼              ▼              ▼
 MySQL 8       Redis         Qdrant        阿里 DashScope
 业务数据      Token/缓存/   文档向量       对话模型 + Embedding
              锁/失败计数    （1024 维）     （text-embedding-v3 / 通义千问）
```

### 2.2 运行环境

| 项 | 开发环境 | 生产环境 |
|----|----------|----------|
| OS | Windows 11 | Linux（CentOS/Ubuntu） |
| JDK | 17 | 17 |
| 构建后端 | Maven 3.9 | Maven / CI |
| 运行后端 | jar 内嵌 Tomcat | jar + Nginx 反代 |
| 数据库 | MySQL 8 | MySQL 8 |
| 缓存 | Redis 8.x | Redis 8.x |
| 向量库 | Qdrant（Docker） | Qdrant（Docker） |
| Node | 22+ | —（仅构建期） |
| 前端构建 | Vite 8 | Vite build → Nginx 静态 |

### 2.3 总体处理流程

**HTTP 请求流转**：

```text
浏览器 → axios（附加 Sa-Token）→ Controller（参数校验）→ Service（业务/事务/权限）
       → Mapper → MySQL；读写 Redis 缓存；按需调用 AI 模块
       → Result 封装 → 响应浏览器
```

**AI 协作流程**：详见需求 V2.1 第 4.3 节；技术实现见本文件第 4 章。

## 3. 后端架构设计

### 3.1 分层架构

| 层 | 职责 | 规范 |
|----|------|------|
| Controller | 接收请求、参数校验（`@Valid`）、调用 Service、封装 Result | 不含业务逻辑；不直接访问 Mapper |
| Service | 业务逻辑、事务控制、权限校验、调用其他模块 Service | 接口 + Impl 分离；事务边界在此层 |
| Mapper | 数据访问（MyBatis-Plus BaseMapper） | 仅 CRUD 与查询，不含业务规则 |

**横切关注点**：操作日志（AOP）、数据范围隔离（AOP）、全局异常处理、Sa-Token 鉴权拦截、MyBatis-Plus 自动填充。

### 3.3 模块划分与依赖

各模块职责详见需求 V2.1 第 5 章，本节给出模块间的依赖关系。**依赖规则**：上层可依赖下层，同层模块仅通过 Service 接口单向依赖，禁止循环依赖。

```text
依赖方向（实线 = 依赖，调用方 → 被依赖方；上层可依赖下层，禁止循环）：

          system   ◄── 被所有业务模块依赖（当前用户、权限、日志、配置）
            │
            ▼
          project  ◄── 业务基础模块，被下列模块依赖（均含 project_id）
            │
            ├── requirement ──┐
            ├── sprint ───────┤
            ├── task ─────────┼──► statistics（聚合查询以上各模块，无独立表）
            ├── bug ──────────┤
            ├── testcase ─────┤
            └── document ─────┘

  关联关系（业务关联，非模块依赖）：
    sprint ◇──◇ requirement     经 sprint_requirement（N : N）
    task / bug / testcase        各自关联 requirement / sprint（可空）

  横向：
    所有业务模块 ──按需──►  ai 模块（AI 经业务 Service 取上下文，不直接写业务表）
    所有模块    ──共享──►  common / framework / config
```

### 3.4 公共组件

| 组件 | 设计要点 |
|------|----------|
| `Result<T>` | 统一响应 `{ code, message, data }`，`code` 见 6.1 |
| `PageResult<T>` | 分页响应 `{ list, total, pageSize, currentPage }` |
| `GlobalExceptionHandler` | 捕获：业务异常 `BizException`、参数校验 `MethodArgumentNotValidException`、Sa-Token 未登录/无权限、乐观锁冲突、其余兜底 500 |
| `BaseEntity` | 公共字段：`id`、`createTime`、`updateTime`、`createBy`、`updateBy`、`version`（乐观锁）、`isDeleted`（逻辑删除 `@TableLogic`）；由 `MetaObjectHandler` 自动填充审计字段 |
| `@OperLog` + `OperLogAspect` | 注解标记需审计的方法，切面记录入 `operation_log` |
| `@DataScope` + `DataScopeAspect` | 数据范围隔离，见 8.3 |

## 4. AI 模块架构设计

AI 模块是本平台的论文亮点，采用**策略模式 + RAG 管道**，业务与 AI 解耦。

### 4.1 总体架构

```text
用户点击 AI 按钮
     │
     ▼
AiController（/api/ai/*）
     │
     ▼
AssistantService ──dispatch──→ AssistantRegistry（按 AiType 分发）
     │                              │
     │               ┌──────────────┼──────────────┐
     │               ▼              ▼              ▼
     │        普通助手(6个)    KnowledgeQaAssistant   （均实现 AiAssistant）
     │               │              │
     │               ▼              ▼
     │        ContextBuilder（组装业务上下文）
     │               │              │
     │               ▼              ▼
     │        PromptManager（渲染 resources/prompt/*.md）
     │               │              │
     │               ▼              ▼
     │        ChatModel（DashScope，流式）  ←─ RetrieveService → Qdrant（仅问答走 RAG）
     │               │              │
     │               ▼              ▼
     │        SseEmitter / Flux<String> → 前端
     │
     ▼
DraftService（采纳 → ai_draft → 二次确认 → 转写正式表）
AiRecordService（全程记录 ai_record）
```

### 4.2 助手抽象（策略模式）

```text
interface AiAssistant {
    AiType type();                    // 助手类型（对应需求 §7.11 枚举）
    DraftTarget target();             // 草稿落点（一次调用可产生多个不同 target_module 的草稿）：需求补充 / 任务 / 测试用例 / Bug 备注 / 迭代总结 / 项目总结 / 问答无草稿
    Flux<String> stream(AiContext ctx); // 流式执行
}

// 7 个实现：
//   RequirementAnalysisAssistant    需求分析
//   TaskBreakdownAssistant          任务拆解
//   TestCaseGenerationAssistant     测试用例生成
//   BugAnalysisAssistant            Bug 分析
//   KnowledgeQaAssistant            知识库问答（走 RAG，无草稿）
//   SprintSummaryAssistant          迭代总结
//   ProjectSummaryAssistant         项目总结
```

`AssistantRegistry` 在启动时收集所有 `AiAssistant` Bean，按 `AiType` 路由。新增助手只需实现接口并注册，符合开闭原则。

### 4.3 Prompt 模板管理

- 模板存放 `resources/prompt/*.md`，**与代码解耦**（满足需求 V2.1 可维护性 §8.4）
- 变量用 `{{var}}` 占位，如 `{{requirement_title}}`、`{{sprint_goal}}`
- `PromptManager` 启动时加载、渲染时填充变量，便于不重启调整

### 4.4 上下文组装（ContextBuilder）

按助手类型查询相关业务数据（**通过调用业务 Service，不直接访问业务表**）：

| 助手 | 组装的上下文 |
|------|--------------|
| 需求分析 | 需求标题、描述、所属项目背景与技术栈 |
| 任务拆解 | 需求内容、迭代目标、迭代内已有任务（避免重复建议） |
| 测试用例生成 | 需求描述、关联接口/业务规则 |
| Bug 分析 | Bug 描述、复现步骤、错误日志、关联需求 |
| 迭代总结 | 迭代需求完成情况、任务统计、Bug 统计、测试执行统计 |
| 项目总结 | 项目各迭代汇总、整体任务/Bug/测试统计 |

上下文长度超限时采用截断或摘要策略，避免超出模型 token 上限。

### 4.5 RAG 管道

#### 文档摄入（离线，文档上传后异步触发）

```text
文档上传（MD/TXT）→ 文本提取 → 切片（300–500 字，重叠 50 字）
   → DashScope Embedding（text-embedding-v3，1024 维）
   → Qdrant upsert（payload: project_id / document_id / chunk_index / content / source_name）
   → document_chunk 表保存片段与向量 ID 关联
   → document.parse_status = 已完成（失败则置「失败」，允许重新解析）
```

#### 检索问答（在线，知识库问答助手）

```text
用户问题 → DashScope Embedding
   → Qdrant 搜索（filter: project_id = 当前项目；topK=5，可配置）
   → 取回片段作为上下文 + 引用来源（文档名 + 片段摘要）
   → ChatModel 生成回答（约束「无匹配则告知未找到相关文档」）
   → 流式返回回答 + 引用
```

#### Qdrant collection 设计

| 项 | 设计 |
|----|------|
| collection 名称 | `dev_assist_chunks` |
| 向量维度 | 1024（与 `text-embedding-v3` 一致） |
| 距离度量 | Cosine |
| HNSW 索引 | `m=16`，`ef_construct=128`，查询 `ef=128` |
| payload 字段 | `project_id`(keyword)、`document_id`(keyword)、`chunk_index`(integer)、`content`(text)、`source_name`(keyword) |
| payload 索引 | `project_id`（keyword 索引，用于按项目过滤） |

> 项目隔离：每次检索强制带 `filter: project_id = 当前用户所属项目`，从数据层保证知识库隔离（对应需求 V2.1 安全性 §8.3）。

### 4.6 SSE 流式输出

- 后端用 `Flux<String>`（WebFlux 风格）或 `SseEmitter` 返回 `text/event-stream`
- 推送格式：`data: {片段}\n\n`，结束发送 `data: [DONE]\n\n`
- 前端 `@microsoft/fetch-event-source` 消费（支持自定义 header 携带 Token，优于原生 EventSource）

### 4.7 草稿机制

```text
ai_draft 状态机：  待确认 ──confirm──→ 已采纳（转写正式表）
                     │
                     └──discard──→ 已丢弃
```

- 用户在抽屉点「采纳选中/全部采纳」→ 批量生成 `ai_draft`（状态「待确认」）
- 用户二次确认 → `DraftConfirmService` 按 `target_module` 分发到对应业务 Service 的创建方法，**事务保证**草稿与正式数据一致；草稿置「已采纳」
- 放弃 → 草稿置「已丢弃」

### 4.8 Tool Calling 设计

仅暴露**只读**工具（LangChain4j `@Tool` 注解），AI 不可直接写库：

| 工具 | 用途 |
|------|------|
| `queryProjectStatistics` | 查询项目统计（供总结助手使用） |
| `querySprintProgress` | 查询迭代进度 |
| `queryRequirementDetail` | 查询需求详情 |

工具内部调用业务 Service 的查询方法，强制只读。

### 4.9 异常降级

对应需求 V2.1 第 6.2.4 节：AI 服务不可用/超时（>30s）/流式中断/格式异常，分别走提示、提示、保留已输出、降级纯文本。降级不影响主体业务流程。

## 6. 接口设计（概要）

### 6.1 接口规范

沿用需求 V2.1 第 14.1 节，补充设计层约定：

- **统一响应** `Result<T> = { code: number, message: string, data: T }`
- **状态码段**：`200` 成功；`401` 未登录；`403` 无权限；`4xx` 客户端错误；`5xx` 服务端错误；业务错误用 `5xx` 段自定义码（如 `50001` 账号锁定）
- **分页响应** `PageResult<T> = { list: T[], total, pageSize, currentPage }`
- **鉴权**：除 `/api/login`、`/api/refresh-token` 外，请求头携带 `Authorization: Bearer <accessToken>`
- **流式**：AI 与知识库问答接口返回 `text/event-stream`

### 6.2 模块接口概览

完整接口清单见需求 V2.1 §14.2（共 74 个），概要设计按模块分组说明职责：

| 模块 | 接口组 | 对应需求章节 |
|------|--------|--------------|
| 认证 | 登录 / 退出 / 刷新 / 改密 / 个人信息 | 4.1 |
| 用户与角色 | 用户 CRUD / 角色查询 / 角色权限分配 | 4.1 |
| 项目 | 项目 CRUD / 状态变更 / 成员管理 | 4.2 |
| 需求 | 需求 CRUD / 状态变更 / 排期 / 评审 | 4.3 |
| 迭代 | 迭代 CRUD / 需求规划 / 进度 / 燃尽图 / 总结 | 4.4 |
| 任务 | 任务 CRUD / 状态变更 / 评论 / 工作记录 | 4.5 |
| 缺陷 | Bug CRUD / 状态变更 / 分配 | 4.6 |
| 测试 | 测试用例 CRUD / 执行 / 历史 | 4.7 |
| 文档 | 文档 CRUD / 下载 / 重新解析 / 知识库问答 | 4.8 |
| 统计 | 项目统计 / 迭代统计 / 成员负载 | 4.9 |
| AI | 7 助手（SSE）/ 草稿 / 记录 | 6 |
| 日志 | 操作日志查询 | 4.10 |

### 6.3 关键接口设计

- **SSE 流式协议**：请求体传业务上下文（如 `{ requirementId }`）；响应 `text/event-stream`，逐片段 `data:` 推送，末尾 `data: [DONE]`
- **文件上传**：`multipart/form-data`，后端校验类型与大小（需求 §5.8），文档上传后**异步**触发解析（`@Async`，不阻塞上传响应）
- **草稿确认**：`POST /api/ai/drafts`（采纳选中→生成草稿）→ `PUT /api/ai/drafts/{id}/confirm`（二次确认→事务转写正式表）

## 7. 数据库设计（概要）

### 7.1 设计规范

| 项 | 规范 |
|----|------|
| 命名 | 表名 `snake_case` 单数；字段 `snake_case`；外键 `xxx_id`；时间 `xxx_time`；状态/类型 `status`/`type` |
| 主键 | `id BIGINT AUTO_INCREMENT` |
| 类型 | 状态/类型 `VARCHAR(32)`（存枚举码）或 `TINYINT`；工时 `DECIMAL(5,1)`；时间 `DATETIME`；长文本 `TEXT` |
| 审计字段 | 所有业务表含 `create_time`/`update_time`/`create_by`/`update_by` |
| 逻辑删除 | `is_deleted TINYINT(1) DEFAULT 0`（MyBatis-Plus `@TableLogic`） |
| 乐观锁 | 可并发修改的表含 `version INT DEFAULT 0`（`@Version`） |
| 字符集 | `utf8mb4` / `utf8mb4_unicode_ci` |

字段清单详见需求 V2.1 第 7 章数据字典，本文档不重复。

### 7.2 实体关系

整体实体关系见需求 V2.1 第 7 章数据字典。核心关系基数：

- `user` 1—N `project`（creator）；`user` N—N `project`（经 `project_member`）
- `project` 1—N `requirement` / `sprint` / `task` / `bug` / `test_case` / `document`
- `sprint` N—N `requirement`（经 `sprint_requirement`）
- `requirement` 1—N `task` / `test_case`；`task` 1—N `work_log` / `task_comment`
- `bug` N—1 `requirement`/`task`/`test_case`（可空）；`test_case` 1—N `test_execution`
- `document` 1—N `document_chunk`
- `ai_record` 1—N `ai_draft`

### 7.3 索引设计策略

- **外键索引**：所有 `xxx_id` 字段建普通索引
- **联合索引**：高频查询维度组合，如 `(project_id, status)`、`(assignee_id, status)`、`(sprint_id, status)`
- **唯一约束**：`user.username`、`(project_id, user_id)`（project_member）、`(role_id, permission_id)`（role_permission）
- **软删除**：联合索引含 `is_deleted` 时注意区分度（毕业设计数据量小，影响可忽略）

详见第 4.5 节。collection `dev_assist_chunks`，1024 维，Cosine 距离，`project_id` 建 payload 索引用于过滤隔离。

## 8. 安全设计

### 8.1 认证设计（Sa-Token JWT 双 Token）

```text
登录 /api/login
   → 校验账号密码（BCrypt）+ 校验账号未禁用/未锁定
   → StpUtil.login(userId) 生成 accessToken
   → 额外签发 refreshToken 存 Redis（key: refresh:{userId}）
   → 返回 { accessToken, refreshToken, expires }

受保护请求
   → SaTokenInterceptor 校验 accessToken 有效 + 未在黑名单

accessToken 过期
   → 前端响应拦截捕获 401
   → 用 refreshToken 调 /api/refresh-token
   → 后端校验 Redis 中 refreshToken 有效 → 签发新 accessToken

登出 /api/logout
   → StpUtil.logout + accessToken 加入 Redis 黑名单至过期

登录失败计数
   → 密码错误 login_fail_count++（Redis），达 5 次设 lock_until = now+30min
```

### 8.2 授权设计

| 层级 | 机制 |
|------|------|
| 菜单权限 | 前端按 `permissions` 动态注册路由（5.4） |
| 操作权限 | 后端 `@SaCheckPermission("requirement:create")`；前端 `v-auth` 指令控制按钮 |
| 角色检查 | `@SaCheckRole` 校验系统角色 |

权限矩阵详见需求 V2.1 第 12 章。

### 8.3 数据隔离设计

项目级行隔离通过 `@DataScope` 注解 + AOP 切面实现，在 SQL 层自动拼接条件：

| 角色 | 自动追加条件 |
|------|--------------|
| 系统管理员 | 无限制（全局） |
| 项目负责人 | `project_id IN (项目成员表 where user_id=当前 and role=负责人)` |
| 开发/测试 | `project_id IN (所属项目)`；任务/Bug 再追加 `assignee_id = 当前` 的写权限边界 |

切面解析当前用户角色与所属项目，生成 SQL 片段注入查询，避免业务代码到处手写权限条件。

### 8.4 其他安全

- 密码 BCrypt 加盐哈希
- 登录失败锁定（8.1）
- 上传文件类型与大小校验（需求 §5.8）
- XSS：前端过滤用户输入，后端参数校验
- SQL 注入：MyBatis 参数化查询
- AI Tool Calling 只读（4.8），禁止 AI 直接写库

## 10. 非功能性设计实现

### 10.1 性能

- **列表分页**：MyBatis-Plus 分页插件，默认每页 20 条（需求 §8.2）
- **索引**：见 7.3 索引策略，覆盖高频查询
- **Redis 缓存**：用户权限、枚举字典、热点统计结果缓存，减少 DB 压力
- **文档异步解析**：`@Async` + 线程池，上传响应不阻塞（AsyncTaskConfig）
- **统计查询**：直接聚合 SQL；若数据量增大可引入预聚合定时任务（本期不做）

### 10.2 可靠性

- **AI 降级**：AI 服务不可用/超时时降级提示，主体业务不受影响（4.9）
- **重试**：AI 调用失败指数退避重试，最多 3 次
- **幂等**：Token 刷新、草稿确认设计为幂等
- **乐观锁**：并发修改冲突时返回提示，要求刷新重试（需求 §4.2）

### 10.3 可维护性

- **模块化**：`modules` 下每业务模块独立子包，边界清晰（需求 §8.4）
- **业务与 AI 解耦**：AI 通过业务 Service 接口取数，不直接操作业务表
- **Prompt 外置**：`resources/prompt/*.md`，与代码分离
- **配置外置**：`application.yaml` + 环境变量
