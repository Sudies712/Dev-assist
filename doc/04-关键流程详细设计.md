## 1. 认证、授权与数据范围隔离

### 1.1 Sa-Token 双 Token 机制

| Token | 用途 | 有效期 | 存储 |
|--------|------|--------|------|
| accessToken | 业务请求鉴权 | 短（如 2h） | Redis（会话）|
| refreshToken | 刷新 accessToken | 长（如 7d） | Redis `refresh:{userId}` |

```
登录  /api/login
  1. BCrypt 校验密码
  2. 校验 status=ENABLED 且未锁定（lock_until <= now）
  3. 失败计数：密码错误 → Redis INCR login_fail:{userId}，达 5 次设 lock_until = now+30min
  4. 成功 → StpUtil.login(userId) 生成 accessToken；另签 refreshToken 存 Redis
  5. 返回 { accessToken, refreshToken, expires, user+roles+permissions }

刷新  /api/refresh-token
  1. 校验 Redis 中 refreshToken 有效且匹配
  2. 签发新 accessToken（refreshToken 可滚动续期）

登出  /api/logout
  → StpUtil.logout + accessToken 加入 Redis 黑名单 blacklist:{tokenValue} 至过期
```

### 1.2 RBAC 三层校验

| 层 | 前端 | 后端 |
|----|------|------|
| 菜单 | 登录后按 `permissions`（MENU 类）动态注册路由 | — |
| 按钮 | `v-auth="'requirement:create'"` 控制显隐 | `@SaCheckPermission("requirement:create")` |
| 角色 | — | `@SaCheckRole("OWNER")` 校验系统角色 |

权限码格式：`模块:操作`（见 schema.sql 初始数据），登录时一次性下发到 `user.permissions`。

### 1.3 数据范围隔离 `@DataScope`

**目标**（SRS §12.2）：项目负责人只见自己负责的项目；开发/测试只见所属项目；管理员全局；任务/Bug 写权限再收敛到 `assignee_id`。

**实现**：基于 MyBatis-Plus 的 `DataPermissionInterceptor` + 自定义 `DataScopeHandler`，对标注 `@DataScope` 的查询方法自动拼接 `project_id` 过滤条件，业务代码零侵入。

```java
// 注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataScope {
    /** SQL 中 project 列的全限定别名，如 "task.project_id" */
    String projectColumn() default "project_id";
}

// 切面/Handler 伪代码（按当前用户角色生成 WHERE 片段）
String buildCondition(LoginUser u) {
    if (u.hasRole("ADMIN")) return null;                          // 无限制
    // 我参与的项目 id 集合（负责人=创建 或 任一项目成员）
    String myProjects = "SELECT id FROM project p WHERE p.creator_id = " + u.getId()
        + " OR EXISTS (SELECT 1 FROM project_member m WHERE m.project_id = p.id AND m.user_id = " + u.getId() + ")";
    return projectColumn + " IN (" + myProjects + ")";
}
```

- 查询接口（需求/任务/Bug/测试/文档/统计列表）标 `@DataScope`，自动收敛到自己可见项目
- **写权限边界**（任务/Bug 的 assignee）在 Service 层显式校验：开发人员仅能改 `assignee_id = 当前用户` 的任务/Bug；项目负责人可改所辖项目任意
- AI 检索/Tool Calling 的项目范围同样强制带 `project_id = 当前选中项目`（见 §4）

## 2. 状态机校验

### 2.1 统一抽象

每类状态机用一个 enum + `nextAllowed()` 方法集中定义合法迁移与前置条件；状态变更 Service 统一走 `StateMachine.check()`，非法迁移抛 `BizException(50004)`。

```java
public interface StateMachine<S extends Enum<S>> {
    /** 当前状态允许的下一状态集合 */
    Set<S> next(S current);
    /** 默认操作人校验交给 Service（结合 SecurityUtils + 权限码） */
}

// 通用状态变更模板
public <S extends Enum<S>> void changeStatus(Long id, S target, Map<String,Object> bizFields) {
    Entity e = mapper.selectById(id);
    S current = Enum.valueOf(type, e.getStatus());
    if (!machine.next(current).contains(target)) throw new BizException(50004, "状态流转非法");
    checkOperatorAuthority(e, target);                 // 操作人 + 必填字段校验
    applySideEffect(e, current, target, bizFields);    // 如写评审记录、退回原因、修复说明
    e.setStatus(target.name());
    mapper.updateById(e);                              // version 乐观锁
    operLogAspect.record(...);                          // 操作日志
}
```

### 2.2 五个状态机的迁移表（汇总自 SRS，编码实现以此为准）

**需求**（操作人：OWNER 为主）
```
PENDING_REVIEW → CONFIRMED | CLOSED(评审不通过)
CONFIRMED      → SCHEDULED(加迭代) | CLOSED
SCHEDULED      → CONFIRMED(移出迭代) | DEVELOPING
DEVELOPING     → TESTING | SCHEDULED(退回)
TESTING        → DONE | DEVELOPING(严重问题退回)
DONE           → CLOSED
CLOSED         → PENDING_REVIEW(重新打开)
```

**任务**
```
TODO            → IN_PROGRESS | CLOSED(取消)
IN_PROGRESS     → READY_FOR_TEST | TODO(退回,填原因) | CLOSED
READY_FOR_TEST  → DONE | IN_PROGRESS(测试不通过退回)   // 测试人员或开发
DONE            → CLOSED
CLOSED          → （终态）
```
> 测试人员仅在 `READY_FOR_TEST` 流转（→ DONE/IN_PROGRESS），与 SRS §12.1 任务权限一致。

**Bug**
```
PENDING_CONFIRM → PENDING_FIX | REJECTED(填拒绝原因)
PENDING_FIX     → FIXING
FIXING          → PENDING_VERIFY(填修复说明)
PENDING_VERIFY  → CLOSED | PENDING_FIX(验证失败,填原因)
CLOSED          → PENDING_CONFIRM(测试人员重新打开)
REJECTED        → PENDING_CONFIRM(测试人员重新激活)
```

**项目**：`NOT_STARTED→IN_PROGRESS→(PAUSED<->IN_PROGRESS)→COMPLETED→ARCHIVED`
**迭代**：`NOT_STARTED→IN_PROGRESS→COMPLETED→ARCHIVED`（不可回退；中止须删迭代退需求）

## 3. AI 草稿二次确认（事务一致性）

### 3.1 全流程

```
AI 助手流式生成 → done 事件返回 items[] + aiRecordId（ai_record.status=UNADOPTED）
   ↓ 用户在抽屉勾选 + 编辑
POST /api/ai/drafts { aiRecordId, items[] }
   → 批量写 ai_draft(status=PENDING_CONFIRM)；ai_record.status 视采纳情况 UNADOPTED/PARTIAL
   ↓ 用户在"AI 记录"页二次确认
PUT /api/ai/drafts/{id}/confirm
   → @Transactional：按 draft.targetModule 调对应业务 Service.create()
   → 写正式表（task/requirement 补充/testcase/bug 备注/sprint|project summary）
   → ai_draft.status=ADOPTED, confirm_time=now
   → 若该 ai_record 下所有 draft 均 ADOPTED/DISCARDED → ai_record.status=FULL
DELETE /api/ai/drafts/{id} → status=DISCARDED
```

### 3.2 关键约束

| 约束 | 实现 |
|------|------|
| **事务** | `DraftConfirmService.confirm()` 标 `@Transactional`，正式数据写入与草稿状态变更同事务；任一失败回滚 |
| **幂等** | confirm 前校验 `ai_draft.status == PENDING_CONFIRM`，已 ADOPTED 则直接返回原 targetId，不重复写 |
| **分发** | `Map<DraftTarget, DraftApplier>` 策略模式，按 `targetModule` 选 Applier（TaskApplier/RequirementApplier/…） |
| **不直接写业务** | AI 生成结果从不直接落业务表，必经草稿（SRS §6.1 约束 2） |

```java
public interface DraftApplier {
    DraftTarget target();
    Long apply(AiDraft draft);   // 返回生成的业务实体 id
}
// TaskApplier: draftContent(JSON) → TaskCreateDTO → TaskService.create → 返回 task.id
```

## 4. RAG 摄入与检索管道

### 4.1 文档摄入（异步，@Async + 线程池 AsyncTaskConfig）

```
文档上传成功（parseStatus=UNPARSED）
  → @Async 异步任务
  → parseStatus=PARSING
  → 1. 文本提取（MD/TXT 直读；后续 Apache Tika 扩展 PDF/DOCX）
  → 2. 切片：按语义/段落边界，每片 300–500 字，相邻片重叠 50 字
  → 3. DashScope EmbeddingModel.embedAll(chunks)   // text-embedding-v3, 1024 维
  → 4. QdrantEmbeddingStore.addAll(embeddings, metadata{project_id, document_id, chunk_index, content, source_name})
  → 5. 回写 document_chunk（content + vector_id + chunk_index）
  → parseStatus=PARSED
  → 异常：parseStatus=FAILED，记录错误信息，允许 /reparse 重试
```

### 4.2 检索问答（在线，知识库问答助手）

```
用户问题 q（强制当前选中项目 projectId）
  → EmbeddingModel.embed(q)
  → QdrantEmbeddingStore.search(embedding,
        filter = match("project_id" = projectId),
        maxResults = 5)                  // Top-K=5，可配
  → 命中为空 → 直接回 "未找到相关文档"，不臆造
  → 命中 → 片段作为上下文 + 引用来源（docName + snippet）拼 prompt
  → ChatModel.stream(prompt)             // SSE delta 推送
  → 推送 sources 事件（引用来源）
  → done（写 ai_record, aiType=KNOWLEDGE_QA）
```

### 4.3 Qdrant collection（与概要 §4.5 一致）

- collection：`dev_assist_chunks`，1024 维，Cosine，HNSW `m=16/ef_construct=128/ef=128`
- payload：`project_id`(keyword, 建索引)、`document_id`(keyword)、`chunk_index`(integer)、`content`(text)、`source_name`(keyword)
- **项目隔离**：摄入与检索都强制带 `project_id`，从数据层保证不跨项目泄露（对应 SRS §8.3 安全）

### 4.4 删除联动
删除 `document` 时：按 `document_id` 从 Qdrant 删除对应 points + 删 `document_chunk` 行（避免向量孤儿）。
