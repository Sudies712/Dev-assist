## 1. 引言

### 1.1 编写目的

本文档对"软件项目开发辅助管理平台"进行完整的需求分析与规格说明，覆盖系统建设目标、用户角色、业务流程、功能需求、数据需求、非功能需求、AI 辅助能力边界及交互规格，为后续概要设计、数据库设计、接口设计、编码实现和系统测试提供依据。

### 1.2 项目背景

软件项目开发涉及需求、任务、缺陷、测试用例和项目文档等多类信息，中小团队或教学实践项目若缺乏统一平台，容易出现需求描述不清、任务分配混乱、缺陷跟踪不及时、测试记录不完整、文档难以复用等问题。

近年来大语言模型和 RAG 技术的发展为软件工程管理流程提供了新的辅助手段。通过 LangChain4j 将大模型能力接入 Spring Boot，可以在不改变平台主体业务流程的前提下，为需求分析、测试用例生成、Bug 原因分析和知识库问答等环节提供智能辅助。

### 1.3 项目定位

本系统以软件项目管理为主体、以 AI 辅助为亮点。平台首先具备完整的 Scrum 项目管理能力（用户权限、项目、需求待办、迭代、任务、缺陷、测试用例、文档、统计），再通过 LangChain4j 实现 AI 辅助需求分析、任务拆解、测试用例生成、Bug 分析和项目知识库问答。

```text
平台业务功能为主体，AI 辅助能力为亮点。
```

### 1.4 适用范围

本文档适用于本项目的需求分析阶段，后续概要设计、详细设计、数据库设计、接口设计、系统实现和测试均可参考本文档。

## 2. 系统建设目标

### 2.1 总体目标

设计并实现一个基于 Spring Boot 与 LangChain4j 的软件项目开发辅助管理平台，覆盖项目创建、成员管理、需求待办、迭代计划、任务分配、缺陷跟踪、测试用例管理、项目文档沉淀和统计分析的完整闭环，并通过 AI 辅助提升需求分析、测试设计、Bug 排查、迭代总结和文档检索效率。

### 2.2 具体目标

| 序号 | 目标 |
|------|------|
| 1 | 实现用户登录和基于角色的权限控制 |
| 2 | 实现项目管理（创建、编辑、成员维护、状态管理） |
| 3 | 实现需求管理（创建、分类、优先级、状态流转、评审记录）和产品待办列表 |
| 4 | 实现迭代管理（创建迭代、设置周期、规划需求与任务、跟踪进度、生成总结） |
| 5 | 实现任务管理（创建、分配、状态流转、评论、工作记录，归属到迭代） |
| 6 | 实现缺陷管理（提交、分配、严重程度、状态流转、修复记录、附件） |
| 7 | 实现测试用例管理（创建、执行、结果记录，关联需求/Bug/迭代） |
| 8 | 实现项目文档管理（上传、分类、解析、检索、知识库问答） |
| 9 | 实现统计仪表盘（项目进度、迭代进度、任务完成率、Bug 分布、测试执行情况） |
| 10 | 引入 LangChain4j，实现 AI 辅助需求分析、任务拆解、测试用例生成、Bug 分析、迭代总结和知识库问答 |
| 11 | AI 生成结果须经用户确认后才能保存为正式业务数据，系统记录完整生成与采纳过程 |

## 3. 用户角色分析

### 3.1 系统管理员

| 属性 | 说明 |
|------|------|
| 职责 | 系统级基础管理 |
| 核心操作 | 管理系统用户；分配系统角色；维护角色权限；查看操作日志；维护基础字典 |
| 数据范围 | 全局 |

### 3.2 项目负责人

| 属性 | 说明 |
|------|------|
| 职责 | 承担 Product Owner（需求待办、优先级）和 Scrum Master（迭代进度、风险跟踪）的管理职责 |
| 核心操作 | 创建和维护项目；添加/移除项目成员并分配项目内角色；创建和维护需求待办列表；设置需求优先级和状态；创建迭代并规划迭代周期；将需求选入迭代；拆解和分配迭代任务；跟踪迭代进度和成员任务负载；查看 Bug、测试和任务统计；使用 AI 生成需求分析、任务拆解、迭代总结和项目总结 |
| 数据范围 | 所管理项目的全部数据 |

### 3.3 开发人员

| 属性 | 说明 |
|------|------|
| 职责 | 完成迭代开发任务和修复缺陷 |
| 核心操作 | 查看参与的项目和当前迭代信息；查看分配给自己的迭代任务；更新任务状态；填写工作记录；查看需求详情；查看和处理分配给自己的 Bug；提交 Bug 修复记录；查看项目文档和使用知识库问答 |
| 数据范围 | 所属项目的需求/任务/Bug（个人分配范围内的可写，其余仅可读） |

### 3.4 测试人员

| 属性 | 说明 |
|------|------|
| 职责 | 迭代需求的测试用例设计、测试执行和缺陷提交 |
| 核心操作 | 查看项目需求和当前迭代需求；编写测试用例；使用 AI 根据需求生成测试用例草稿；执行测试用例并记录结果；提交 Bug；验证 Bug 修复结果；查看测试执行统计和迭代质量统计 |
| 数据范围 | 所属项目的需求/测试用例/Bug（用例可编辑、执行，Bug 可提交和验证） |

## 4. 业务流程分析

### 4.1 Scrum 主流程

```text
用户登录
→ 创建项目
→ 添加项目成员并分配项目内角色
→ 创建和维护需求待办列表（Product Backlog）
→ [AI 辅助分析需求]
→ 用户确认需求分析结果并保存
→ 设置需求优先级和状态
→ 创建迭代（Sprint），设定迭代周期和目标
→ 选择需求进入迭代（生成 Sprint Backlog）
→ [AI 辅助拆解迭代任务]
→ 分配任务给开发人员
→ 迭代执行：开发人员更新任务状态、填写工作记录
→ [测试人员根据迭代需求设计测试用例 / AI 辅助生成测试用例草稿]
→ 执行测试用例，记录结果
→ [测试失败则提交 Bug，关联到需求/任务/迭代]
→ [AI 辅助分析 Bug 原因]
→ 开发人员修复 Bug，测试人员验证修复
→ [Bug 验证未通过则重新打开]
→ 迭代评审与总结（[AI 辅助生成迭代总结草稿]）
→ 项目文档沉淀和知识库更新
→ 查看项目统计与迭代仪表盘
```

### 4.2 反向与异常流程

| 场景 | 处理规则 |
|------|----------|
| 需求从迭代移除 | 状态退回"已确认"，回到待办列表，记录操作人和时间 |
| 任务从"进行中"退回"待处理" | 开发人员可退回本人任务、项目负责人可退回任意任务，须填写原因 |
| Bug 被拒绝修复 | 需填写拒绝原因，测试人员可重新激活（状态 → "待确认"） |
| Bug 验证未通过 | 状态退回"待修复"，保留验证失败的备注 |
| 迭代中需求变更 | 迭代开始后不建议频繁调整；确需调整须记录操作日志，关联任务同步评估 |
| 重复操作冲突 | 后端基于乐观锁（版本号）防止并发覆盖，冲突时提示用户刷新后重试 |
| AI 生成超时 | 前端显示"生成超时，请重试"，不遗留半成品数据在界面 |
| AI 返回格式异常 | 降级展示为纯文本，标注"原始输出"，用户仍可手动编辑后采纳 |

### 4.3 AI 辅助处理流程

```text
用户触发 AI 功能（在业务页面点击按钮）
→ 系统组装提示词（含当前项目/迭代/业务数据）
→ 调用 AI 服务（后端 → LangChain4j → ChatModel，支持流式输出）
→ AI 返回结构化建议
→ 系统在侧边抽屉或内联面板中展示生成结果
→ 用户逐条审核：可编辑、可删除、可选择部分采纳
→ 用户点击"确认采纳" → 对应数据写入正式业务表
→ 用户点击"放弃"或关闭面板 → 草稿丢弃
→ 系统记录 AI 生成过程（输入、输出、功能类型、采纳状态、操作时间）
```

## 5. 功能性需求

### 5.1 用户登录与权限管理

#### 5.1.1 用户登录

- 支持账号密码登录
- 登录成功返回用户信息和访问凭证（JWT Token）
- 支持登录状态保持（Token 刷新机制）
- 支持退出登录
- 登录失败给出明确提示（"账号不存在""密码错误""账号已禁用"）
- 未登录用户访问任何内部路由时重定向到登录页

#### 5.1.2 用户管理（系统管理员）

- 新增用户（账号、姓名、初始密码）
- 编辑用户信息
- 禁用或启用用户
- 重置用户密码
- 按用户名、角色、状态筛选查询

#### 5.1.3 角色权限管理

采用 RBAC 模型，系统预置四个角色：系统管理员、项目负责人、开发人员、测试人员。权限分为菜单权限（控制可访问的页面）和操作权限（控制增删改查审批等按钮行为）。

权限矩阵详见第 12 章。

---

### 5.2 项目管理

#### 5.2.1 项目创建与维护

- 创建项目（名称、描述、起止时间、技术栈）
- 编辑项目信息
- 设置项目状态：`未开始 → 进行中 → 暂停 → 已完成 → 已归档`
- 查看项目详情（含成员列表、需求/任务/Bug 统计摘要）
- 归档项目（归档后数据只读）

项目状态转换：

```text
未开始 ──→ 进行中 ──→ 已完成 ──→ 已归档
              │                      ↑
              └──→ 暂停 ──→ 进行中 ──┘
```

#### 5.2.2 项目成员管理

- 添加项目成员（从系统用户中选取）
- 移除项目成员（须确认无未完成任务）
- 设置成员在项目中的角色（项目负责人/开发人员/测试人员）
- 查看项目成员列表及其任务负载

---

### 5.3 需求管理

#### 5.3.1 需求创建与维护

- 创建需求（标题、描述、类型、优先级、预估工作量）
- 编辑需求信息
- 查看需求详情及变更历史
- 关闭/删除需求（已排期需求不可删除，只能关闭）

需求状态：`待评审 → 已确认 → 已排期 → 开发中 → 测试中 → 已完成 → 已关闭`

需求优先级：`低 / 中 / 高 / 紧急`

#### 5.3.2 需求状态转换矩阵

```text
                 ┌─ 已关闭 ←──────────────────────┐
                 │                                  │
待评审 ──→ 已确认 ──→ 已排期 ──→ 开发中 ──→ 测试中 ──→ 已完成
  │          │         │          │         │         │
  └──→ 已关闭(评审不通过)    │    └──→ 已排期(退回)  │
                             └──→ 已确认(移出迭代)    │
```

| 当前状态 | 允许的下一状态 | 操作人 | 条件 |
|----------|---------------|--------|------|
| 待评审 | 已确认、已关闭 | 项目负责人 | |
| 已确认 | 已排期、已关闭 | 项目负责人 | 已排期 = 加入迭代 |
| 已排期 | 已确认、开发中 | 项目负责人/开发人员 | 已确认 = 从迭代移除 |
| 开发中 | 测试中、已排期 | 开发人员/项目负责人 | |
| 测试中 | 已完成、开发中 | 测试人员 | 开发中 = 测试发现严重问题 |
| 已完成 | 已关闭 | 项目负责人 | |
| 已关闭 | 待评审 | 项目负责人 | 重新打开 |

#### 5.3.3 需求待办列表

- 按项目查看需求待办列表（状态为"待评审""已确认""已排期"的需求）
- 支持按优先级、状态、创建时间筛选和排序
- 已关闭/已完成需求不出现在待办列表

#### 5.3.4 需求排期

- 项目负责人选择一个或多个已确认需求加入指定迭代
- 一个需求同一时间只能归属一个"未完成"迭代
- 加入迭代后需求状态自动变为"已排期"
- 需求从迭代移除后状态退回"已确认"，回到待办列表
- 系统记录需求加入/移除迭代的时间和操作人

#### 5.3.5 需求评审记录

- 记录评审人、评审时间、评审意见、评审结果（通过/不通过）
- 支持查看需求评审历史

详见第 6 章 AI 辅助功能需求。

### 5.4 迭代管理

#### 5.4.1 迭代创建与维护

- 创建迭代（名称、目标、开始时间、结束时间、所属项目）
- 编辑迭代基本信息（未开始状态可编辑，进行中仅可编辑目标描述）
- 删除未开始迭代

迭代状态：`未开始 → 进行中 → 已完成 → 已归档`

迭代状态转换：

```text
未开始 ──→ 进行中 ──→ 已完成 ──→ 已归档
              │
              └──→ (不可回退；确需中止则整体删除迭代，需求退回待办)
```

#### 5.4.2 迭代需求规划

- 从项目需求待办列表中选择需求加入迭代
- 查看当前迭代需求列表及完成情况
- 支持从迭代中移除未开始开发的需求（需求状态退回"已确认"）
- 迭代开始后不建议频繁调整；确需调整须记录操作日志

#### 5.4.3 迭代任务规划

- 根据迭代需求创建任务（任务须归属到具体迭代）
- 支持 AI 根据迭代需求和已有模块生成任务拆解建议（见第 6 章）
- 查看迭代任务列表，按负责人、状态、优先级筛选
- 统计迭代任务完成率

#### 5.4.4 迭代执行跟踪

- 查看迭代当前进度（需求完成率、任务完成率）
- 查看迭代内需求、任务、Bug、测试用例执行情况
- 展示简化燃尽图（横轴为迭代天数，纵轴为剩余任务数，含理想线和实际线）
- 识别延期任务、未完成需求和阻塞 Bug
- 查看成员在当前迭代中的任务负载

#### 5.4.5 迭代总结

- 迭代结束后生成迭代总结，包含完成需求数、完成任务数、遗留 Bug、测试情况和风险说明
- 支持 AI 基于迭代数据生成总结草稿（见第 6 章）
- 项目负责人可修改并保存；保存后可作为项目文档沉淀

### 5.5 任务管理

#### 5.5.1 任务创建与分配

- 创建任务（标题、描述、优先级、截止时间、预估工时）
- 关联项目、需求和迭代
- 分配任务负责人
- 查看任务详情、编辑任务信息

任务状态：`待处理 → 进行中 → 待测试 → 已完成 → 已关闭`

#### 5.5.2 任务状态转换矩阵

```text
待处理 ──→ 进行中 ──→ 待测试 ──→ 已完成 ──→ 已关闭
  │          │                              ↑
  └──────────┴──────────→ 已关闭(取消) ─────┘
```

| 当前状态 | 允许的下一状态 | 操作人 |
|----------|---------------|--------|
| 待处理 | 进行中、已关闭 | 开发人员/项目负责人 |
| 进行中 | 待测试、待处理、已关闭 | 开发人员/项目负责人 |
| 待测试 | 已完成、进行中 | 测试人员 |
| 已完成 | 已关闭 | 项目负责人 |
| 已关闭 | —（终态） | — |

#### 5.5.3 任务评论与工作记录

- 任务下可发表评论
- 开发人员可填写工作记录（工作内容、耗时、提交时间）
- 工作记录归属到具体迭代
- 项目负责人可查看成员工作记录汇总

#### 5.5.4 AI 任务拆解

详见第 6 章。

### 5.6 缺陷管理

#### 5.6.1 Bug 提交

- 提交 Bug（标题、描述、复现步骤、严重程度、优先级、截图或日志附件）
- Bug 可关联项目、迭代、需求、任务或测试用例
- 迭代测试过程中发现的 Bug 默认归属当前迭代
- 提交后默认进入"待确认"状态

Bug 状态：`待确认 → 待修复 → 修复中 → 待验证 → 已关闭 / 拒绝修复`

严重程度：`轻微 / 一般 / 严重 / 致命`

#### 5.6.2 Bug 状态转换矩阵

```text
待确认 ──→ 待修复 ──→ 修复中 ──→ 待验证 ──→ 已关闭
  │          │                     │           ↑
  └──→ 拒绝修复                    └──→ 待修复(验证未通过)
```

| 当前状态 | 允许的下一状态 | 操作人 | 条件 |
|----------|---------------|--------|------|
| 待确认 | 待修复、拒绝修复 | 项目负责人 | 拒绝修复须填写原因 |
| 待修复 | 修复中 | 开发人员 | |
| 修复中 | 待验证 | 开发人员 | 须填写修复说明 |
| 待验证 | 已关闭、待修复 | 测试人员 | 待修复 = 验证失败 |
| 已关闭 | 待确认 | 测试人员 | 重新打开 |
| 拒绝修复 | 待确认 | 测试人员 | 重新激活 |

#### 5.6.3 Bug 分配与修复

- 项目负责人将 Bug 分配给开发人员

- Bug 状态变化同步影响迭代质量统计
- 未关闭 Bug 在迭代总结中列为遗留问题
- 系统记录 Bug 状态流转历史

#### 5.6.4 AI Bug 分析

详见第 6 章。

#### 5.7.1 测试用例创建

- 关联项目、需求和迭代
- 可从当前迭代需求快速创建测试用例
- 查看、编辑和删除测试用例

测试用例优先级：`低 / 中 / 高`

#### 5.7.2 测试用例执行

### 5.8 项目文档与知识库管理

#### 5.8.1 文档上传与管理

- 上传项目文档（Markdown、TXT，后续可选支持 PDF、DOCX）
- 设置文档名称、类型、所属项目、描述
- 文档类型：`需求文档 / 设计文档 / 接口文档 / 测试文档 / 会议纪要 / 开发规范 / 迭代总结 / 项目总结 / 其他`
- 支持文档下载、删除和分类查询

#### 5.8.2 文档解析与向量化

- 系统对上传文档进行文本解析
- 将文档内容按语义边界切分为文本片段（每个片段 300-500 字，保留 50 字重叠）
- 调用 Embedding 模型（阿里 DashScope text-embedding-v3，1024 维）生成向量
- 向量保存至向量数据库 Qdrant
- 保存文档片段与原文档的关联关系

#### 5.8.3 项目知识库问答

流程：

```text
用户输入问题
→ 系统将问题向量化
→ 从向量数据库检索 Top-K（K=5）相关文档片段（限定当前项目范围）
→ 将检索结果作为上下文提交给大模型
→ 大模型生成回答
→ 系统展示回答及引用来源（文档名称 + 相关片段摘要）
```

要求：
- 用户只能查询有权限访问的项目知识库
- 回答应优先基于项目文档内容，无匹配时明确告知"未找到相关文档"
- 展示引用来源，降低无依据回答
- 记录用户问题和 AI 回答（用于后续效果评估）

## 6. AI 辅助功能需求

### 6.1 AI 功能总体约束

1. AI 功能嵌入需求、迭代、任务、测试、Bug、文档知识库和统计等业务模块，不设独立聊天页面
2. AI 生成内容**不直接写入**核心业务数据库
3. AI 生成结果须支持用户编辑、删除、部分采纳和确认
4. 系统记录 AI 调用的输入、输出、功能类型、采纳状态、操作人、操作时间
5. AI 回答应结合当前项目、当前迭代和相关业务上下文
6. 知识库问答须展示引用来源
7. 迭代总结/项目总结应基于系统内真实的业务数据（任务、Bug、测试用例等统计）生成

### 6.2 AI 交互规格

#### 6.2.1 触发方式

| 助手 | 触发位置 | 触发控件 |
|------|----------|----------|
| 需求分析助手 | 需求详情页 | "AI 分析"按钮 |
| 任务拆解助手 | 需求详情页 / 迭代详情页 / 任务列表页 | "AI 拆解任务"按钮 |
| 测试用例生成助手 | 需求详情页 / 测试用例列表页 | "AI 生成用例"按钮 |
| Bug 分析助手 | Bug 详情页 | "AI 分析"按钮 |
| 知识库问答助手 | 文档知识库页面 | 搜索/输入框 |
| 迭代总结助手 | 迭代详情页 / 仪表盘 | "生成迭代总结"按钮 |
| 项目总结助手 | 仪表盘 | "生成项目总结"按钮 |

#### 6.2.2 展示容器

- 非问答类（需求分析、任务拆解、测试用例生成、Bug 分析、迭代总结、项目总结）：**右侧抽屉（Drawer）**，宽度约占屏幕 40%-50%
- 知识库问答：**内联聊天面板**（类似对话框，位于知识库页面下部或侧边）

#### 6.2.3 采纳流程

1. AI 结果在容器中以**结构化列表**展示（每条建议前有复选框）
2. 用户可逐条操作：
   - **编辑**：点击进入行内编辑，修改文本后确认
   - **删除**：移除该条建议
   - **全部采纳**：一键采纳所有建议
   - **选择性采纳**：勾选部分条目后点击"采纳选中"
3. 用户点击"采纳选中"后，系统批量创建对应的草稿记录，状态设为"待确认"
4. 用户在草稿列表中再次确认后保存为正式数据（需求补充说明、任务、测试用例、Bug 备注等）
5. 关闭抽屉或点击"放弃"丢弃未采纳的草稿

#### 6.2.4 异常处理

| 异常 | 处理方式 |
|------|----------|
| AI 服务不可用 | 弹出提示"AI 服务暂时不可用，请稍后重试"，不展示抽屉 |
| 生成超时（>30s） | 前端显示"生成超时，请重试"，不展示抽屉 |
| 流式输出中断 | 已输出的部分保留在界面，标注"生成未完成"，用户可选择采纳已完成部分 |
| 返回格式解析失败 | 降级展示原始文本，标注"自动解析失败，请手动编辑" |

#### 6.2.5 AI 生成记录

| 字段 | 说明 |
|------|------|
| 所属项目 | 关联的项目 ID |
| 所属迭代 | 关联的迭代 ID（可为空） |
| 使用模块 | 需求/迭代/任务/测试/Bug/文档/统计 |
| AI 功能类型 | 需求分析/任务拆解/测试用例生成/Bug分析/知识库问答/迭代总结/项目总结 |
| 输入内容 | 提交给 AI 的提示词（含业务上下文） |
| 输出内容 | AI 返回的原始结果 |
| 创建用户 | 触发 AI 功能的用户 ID |
| 创建时间 | 触发时间 |
| 是否采纳 | 布尔值，"部分采纳""全部采纳"或"未采纳" |
| 采纳时间 | 用户确认采纳的时间 |

### 6.3 各 AI 助手输入输出规格

| AI 助手 | 输入 | 输出 | 使用位置 |
|----------|------|------|----------|

## 8. 非功能性需求

### 8.1 易用性

- 界面简洁清晰，功能入口明确，减少深层嵌套导航
- 常用操作不超过 3 步
- 表单提供实时校验和错误提示
- AI 生成结果以结构化方式展示（列表+复选框），便于查看和选择
- 统计图表直观展示项目状态，鼠标悬停显示详情

### 8.2 性能需求

| 指标 | 要求 |
|------|------|
| 列表查询（含筛选）响应时间 | < 2s |
| 统计仪表盘数据加载 | < 3s |
| AI 流式输出首 token 时间 | < 3s |
| 文档语义检索 Top-K | < 2s |
| 单次请求文件上传上限 | 10 MB |
| 支持并发用户数 | ≥ 50（毕业设计演示场景） |
| 全部列表接口 | 分页，默认每页 20 条 |

### 8.3 安全性需求

- 用户必须登录后才能访问系统功能（Sa-Token 认证，JWT 模式双 Token）
- 不同角色有不同菜单和操作权限（见第 12 章权限矩阵）
- 用户只能访问有权限的项目数据（数据行级隔离）
- 密码使用 bcrypt 加密存储
- 登录失败锁定：同一账号连续 5 次密码错误锁定 30 分钟
- 退出登录时将 Token 加入 Redis 黑名单直至过期
- 上传文件限制类型（Markdown, TXT, PDF, DOCX, PNG, JPG）和大小（≤10MB）
- 重要操作（删除、状态变更、权限修改）须记录操作日志
- AI Tool Calling 仅限查询操作，不允许 AI 直接修改数据库
- 前端对用户输入做基本 XSS 过滤，后端对所有接口输入做参数校验

### 8.4 可维护性

- 后端模块化结构：用户模块、项目模块、需求模块、迭代模块、任务模块、缺陷模块、测试模块、文档模块、AI 模块、统计模块、日志模块，边界清晰
- 业务模块与 AI 模块解耦（AI 模块通过接口调用，不直接操作业务表）
- Prompt 模板独立维护（配置文件或数据库存储，不与业务代码耦合）
- 公共响应封装、异常统一处理、权限校验通过拦截器统一实现

### 8.5 可扩展性

后续可扩展方向（非本期范围）：
- 消息通知（任务分配、Bug 分配时通知）
- 任务看板拖拽
- 迭代容量评估和自动风险提醒
- 文档版本管理
- 多轮 AI 对话
- 与代码仓库或 CI/CD 工具集成

## 14. 接口清单

### 14.1 接口规范

- 风格：RESTful，路径前缀 `/api`（前端 axios baseURL 统一添加）
- 认证：除登录、刷新 Token 外，所有接口须携带 Sa-Token（请求头 `Authorization: Bearer <accessToken>`）
- 统一响应：`{ code, message, data }`；分页响应：`{ code, message, data: { list, total, pageSize, currentPage } }`
- 列表接口默认每页 20 条，支持筛选参数
- 文件上传 `multipart/form-data`；AI 与知识库问答接口返回 `text/event-stream`（SSE），按 `data: {...}\n\n` 分块推送，末尾发送 `[DONE]`

## 15. 附录：技术决策项

> 原 V2.0 待确认项第 1–4 项已收敛（见 §9.1），此处保留决策记录与剩余方向性建议。

| 序号 | 决策事项 | 影响范围 | 结论 |
|------|----------|----------|------|
| 1 | 认证方案：Sa-Token vs Spring Security + JWT | 用户模块、安全架构 | **已定**：Sa-Token（JWT 模式，双 Token） |
| 2 | 向量数据库：Qdrant vs pgvector | 文档模块、部署架构 | **已定**：Qdrant（主体库为 MySQL，pgvector 需额外引入 PostgreSQL 实例） |
| 3 | 文档格式：Markdown/TXT vs 同时 PDF/DOCX | 文档模块工作量 | **已定**：MVP 仅 Markdown/TXT，后续 Apache Tika 扩展 |
| 4 | AI 模型：本地 vs 第三方 API vs 多模型 | AI 模块架构、成本 | **已定**：第三方 API（阿里通义千问）；Embedding 用 DashScope text-embedding-v3（1024 维） |
| 5 | 流式输出范围：全部 AI 功能 vs 仅长文本 | 前端 SSE 工作量 | 方向：全部 AI 功能支持流式，前端统一 SSE Hook（fetch-event-source） |
| 6 | 迭代周期：固定 vs 自定义 | 迭代模块校验 | 方向：项目负责人自定义，不做硬限制 |
| 7 | 任务看板拖拽是否纳入 MVP | 前端工作量 | 方向：MVP 后加分项（vuedraggable 已具备，成本低） |
| 8 | AI 采纳率统计是否纳入仪表盘 | 统计模块 | 方向：纳入，作为 AI 效果可视化依据 |

## 16. 验收标准

1. 用户能正常登录系统，并根据角色访问对应功能（验证权限矩阵中每个 R 权限）
2. 项目负责人能创建项目、添加成员、维护需求待办列表和设置优先级
3. 项目负责人能创建迭代、设置周期、选择需求进入迭代并拆解任务
4. 开发人员能查看当前迭代任务、更新任务状态、处理分配给自己的 Bug
5. 测试人员能根据迭代需求创建和执行测试用例、提交 Bug、验证修复
6. Bug 完成完整的状态流转（待确认 → 待修复 → 修复中 → 待验证 → 已关闭），关联关系可追溯
7. 上传 Markdown/TXT 文档后可被解析和向量化，知识库问答返回基于文档的回答并展示引用来源
8. AI 需求分析生成结构化结果（功能点 + 用户故事 + 验收标准），用户可编辑后确认
9. AI 任务拆解和测试用例生成以草稿形式展示，用户可选择部分采纳后保存
10. AI Bug 分析生成可能原因和修复建议，用户可保存为 Bug 备注
11. AI 迭代总结基于真实迭代数据生成草稿，项目负责人可修改并保存
12. AI 生成内容未经用户确认不会写入正式业务表
13. 仪表盘展示项目需求、任务、Bug、测试用例统计信息，含燃尽图
14. 系统在浏览器中运行稳定，Scrum 主流程可完整演示（创建项目 → 需求 → 迭代 → 任务 → Bug → 测试 → 总结）
